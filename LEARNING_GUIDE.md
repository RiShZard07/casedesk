# Understand before interviewing

This project was generated with substantial AI assistance. Do not say you independently designed or wrote it all. Run it, inspect it, and implement a change before claiming proficiency.

1. **Trace one request.** Follow the browser form through URL encoding, `handle`, `form`, `Store.create`, JSON serialization and `textContent` rendering.
2. **Explain OOP choices.** `Store` encapsulates state; an immutable `Ticket` record is replaced on transition. Why is an old snapshot unchanged after a claim?
3. **Explain the heap.** Priorities sort descending, sequence ascending. Create two priority-3 tickets then one priority-5 ticket; predict the claim order. Why not a FIFO queue?
4. **Explain races.** Without one lock, two requests can both miss the same key and create duplicate tickets. Explain why a concurrent map alone would not make the multi-structure operation atomic.
5. **Explain idempotency.** Retry one key; change its title; close its ticket and retry again. Explain 200 vs 409 and current-state vs byte-for-byte response replay.
6. **Explain HTTP.** What distinguishes malformed input, state conflict, missing record, method mismatch, unsupported content type and oversized request?
7. **Review generated code critically.** Why does the UI use `textContent`? What security problems remain? Why is localhost not equivalent to a production security model?
8. **Change something real.** Add an optional category with validation, tests and UI. Or implement queue aging with a clear deterministic clock policy. Do not merely change labels.
9. **Telemetry.** Why are duration and request count not a fully consistent snapshot? What latency percentiles cannot be computed from only a sum?
10. **Persistence and recovery.** Read `Journal.java` and `Store.open`. Explain, in order: why the journal line is written and fsync'd *before* memory changes (what would go wrong the other way round); why replay and live requests share one `apply` method, and why the title and priority limits live in the `Ticket` record's compact constructor rather than only in `create` (what a hand-edited journal line could otherwise load); why only the last line may be torn and why a bad line in the middle must fail startup; what the temp-file + atomic rename in `rewrite` protects against; and why `claim` journals the ticket id rather than "claim the top of the heap". Then break it on purpose: kill the server mid-use, append half a line to the journal, restart, and watch the test "torn tail line is dropped and repaired" in your head. Typical interview questions: "What is a write-ahead log?", "What happens if the disk is full?" (503, memory untouched, test "failed journal write leaves state unchanged"), "How big does the file get?" (bounded at startup compaction, unbounded between restarts), "Why not SQLite?" (no dependency, explicit durability rule; SQLite is the documented next step behind the same `apply` path).
10b. **SQL extension.** Sketch normalized ticket, idempotency-key and state-transition tables for the SQLite version. Explain unique keys, transactions and how `Store.open` would change if recovery came from a `SELECT` instead of a replay.
11. **React.** Trace a controlled title field through `useState`, submission, fetch, and a refreshed table. Explain what `useEffect` cleanup prevents, why a `useRef` lock complements asynchronous state, and why both browser-side guards and backend idempotency matter. Reproduce the lost-response browser scenario. The backend half of a status filter exists (`GET /tickets?state=`, see `stateFilter` and its HTTP test); wire a `<select>` in `App.jsx` to it and add a Playwright scenario yourself.

Interview framing: describe it as an AI-assisted local Java prototype (ChatGPT/Codex for the first draft, Claude Code for the journal), then explain the pieces you personally inspected, tested or changed. No real-user, deployment, business-impact, or performance claims have been established.
